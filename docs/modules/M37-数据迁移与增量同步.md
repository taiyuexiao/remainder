# 模块：数据迁移与增量同步

> 状态：🚧 开发中
> 最近更新：2026-09-26

## 摘要
将当前本地 Remainder 数据一次性导入 `spl` 云端账号；之后新设备登录只下载云端数据并进行业务记录级增量同步，支持断网写入队列和 last-write-wins。

## 动机
当前 `/api/sync` 和 `scripts/data-sync.mjs` 通过 Git 同步整个 `server/data/`，适合单人备份，不适合多用户账号、附件权限、离线队列和冲突审计。

## 范围与非范围
- 范围内：迁移快照、附件清单/哈希、记录增量、变更队列、幂等重放、冲突审计、云端一致性验收。
- 明确不做：CRDT、逐字段合并、多人实时协同；冲突采用服务端 last-write-wins 并保留审计。

## 上下游依赖
- 上游：账号模块、PostgreSQL、对象存储、现有 SQLite schema v18。
- 下游：desktop 离线缓存、同步 API、备份恢复。

## 关键接口与运行时信息
- 关键文件：`server/src/sync/`、`server/src/routes/sync.ts`、`scripts/migrate-local-to-cloud.*`。
- API：`POST /api/sync/push`、`GET /api/sync/pull`、`GET /api/sync/status`、`POST /api/sync/import-snapshot`。
- 变更：`change_id`、`entity_type`、`entity_id`、`operation`、`revision`、`updated_at`、`updated_by`、`payload_hash`。
- 附件：对象存储 key + SHA256 + 大小 + MIME；原始 `.db` 只用于备份恢复。
- 迁移门槛：冻结写入 → 本地备份 → 导入 `spl` → 云端重新导出 → 表数/行数/规范化内容哈希/附件哈希全量比对 → 解冻同步。

## 设计决策与假设
- 首次迁移只发生一次：当前设备本地数据导入 `spl`；后续注册用户不上传本地库。
- 云端账号是 steady-state 真相源；本地 SQLite 是离线缓存。
- “所有数据同步”指所有业务域和用户附件，不指多设备直接上传/下载原始 SQLite 文件。
- 变更队列必须幂等；服务端按记录 last-write-wins，失败不丢队列。

## Bug 与问题记录
### BUG-001 整库 Git 同步可能覆盖多设备修改（2026-09-26，待迁移）
- 错误行为：WHEN 两台设备先后修改同一 SQLite 数据库 THEN Git last-write-wins 可能覆盖未同步的业务记录。
- 期望行为：WHEN 设备联网 THEN 系统 SHALL 按业务记录增量同步并记录冲突审计。
- 不可破坏的行为：WHEN 迁移尚未完成 THEN 系统 SHALL CONTINUE TO 保留本地备份且不得删除原始数据。
- 根因：同步单位是整个 SQLite 文件，无法表达记录级归属和冲突。
- 解决方式：实现记录级 change log、幂等 push/pull 和迁移一致性验收。
- 验证方式：双设备离线修改同一记录，联网后确认最终值符合 last-write-wins 且审计可追溯。
