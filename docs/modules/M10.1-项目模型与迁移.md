# M10.1 项目模型与迁移（后端）

## 1. 任务背景

M10「项目文件夹」：v1 模型把 main/side/follow 任务与零碎想法混在一张 tasks 表里，没有「项目 → 子任务」层级，跟进（follow_ups）也只能挂在单任务上。用户确认的新模型：

- 新增 `projects` 表（项目文件夹），main/side/follow 三类任务整体升级为项目；
- `tasks` 表退化为**子任务 + 想法（idea）**，新增 `project_id` 可空列；idea 任务 `project_id` 为 NULL 平铺；
- 跟进数据（follow_ups）挂到**项目级**，一键再催作用于项目；
- 删项目不删子任务：子任务 `project_id` 置 NULL、`type` 置 `'idea'`（落入想法区，不丢数据）。

库中已有 M1.3 以来的真实数据，迁移必须平滑、幂等。

## 2. 目标

1. `user_version=2` 迁移：旧 main/side/follow 任务原样（保留 id）迁入 projects，follow_ups 数据不丢、FK 改指 projects(id)；
2. 项目/子任务/想法 CRUD、today 视图、一键再催、inbox 转换全部符合新模型；
3. `pnpm --filter server build` 0 错误，`server/verify-m10.ps1` 全链路输出 `M10.1 ALL PASS`。

## 3. 需求

- projects 表：id/name/type(main|side|follow)/status/priority/ddl/milestone/tags/note/created_at/updated_at/done_at；
- `GET /api/projects`：带 done_count/total_count（子任务进度）和 follow 字段（person/next_follow_date/urge_count/last_urged_at），支持 ?type=&status=，默认排除 archived；
- `POST /api/projects`：follow 型必填 person + nextFollowDate（400 校验）；
- `PATCH /api/projects/:id`：含 follow 字段 upsert（只传一个字段时与现有行合并）；
- `POST /api/projects/:id/done`；`DELETE /api/projects/:id`：子任务落 idea、follow_ups 行级联删除；
- `POST /api/tasks`：传 projectId → 子任务（type 从项目继承）；不传时 type 必须是 'idea'（否则 400 并提示走 /api/projects）；
- today 视图统一走 `services/today.ts` 的 `getTodayView()`：overdue/today = 子任务+idea（JOIN projects 带 project_name），followUps = follow 型**项目**（select 带 `p.name AS title` 兼容报表/LLM）；routes/tasks.ts、routes/report.ts、scheduler/index.ts 三处调用同一函数；
- inbox convert：body.projectId → 进已有项目为子任务；不传时 main/side/follow 新建同名项目、idea 平铺；
- urge（`/api/follow-ups/:taskId/urge`）作用于项目 id。

## 5. 实现方案

### 5.1 迁移设计（重点，schema.ts migrateToV2）

由 `PRAGMA user_version` 把关保证幂等（`< 2` 才执行，完成后置 2）：

1. `PRAGMA foreign_keys = OFF`（必须在事务外设置，事务内 PRAGMA 无效）；
2. 事务内：
   - `CREATE TABLE IF NOT EXISTS projects`（新表）；
   - `INSERT INTO projects (id,name,...) SELECT id,title,... FROM tasks WHERE type IN ('main','side','follow')` —— **保留原 id**，列名映射 tasks.title → projects.name；
   - **重建 follow_ups**：先 `CREATE TABLE follow_ups_new`（FK 指向 `projects(id) ON DELETE CASCADE`），`INSERT ... SELECT * FROM follow_ups` 拷贝，再 `DROP` 旧表、`RENAME`。必须先拷贝再动 tasks——否则旧 FK 的 ON DELETE CASCADE 会在删 tasks 行时把跟进数据级联删掉（本迁移 foreign_keys=OFF 双保险）；
   - `DELETE FROM tasks WHERE type IN ('main','side','follow')`；
   - `ALTER TABLE tasks ADD COLUMN project_id TEXT`（先查 `PRAGMA table_info(tasks)` 判断列是否已存在，兼容半迁移状态）；
   - 索引：idx_tasks_project、idx_projects_type、重建 idx_follow_next；
3. 事务提交后 `PRAGMA foreign_keys = ON`、`PRAGMA user_version = 2`。

全新库路径：v1 建表（CREATE IF NOT EXISTS）→ user_version=0 → 立即走 migrateToV2，空数据空迁移，同样落到 v2。

### 5.2 API 语义

- 项目行的 follow 字段通过 `LEFT JOIN follow_ups` 带出；PATCH 的 follow upsert 先读现有行合并再 `INSERT ... ON CONFLICT(task_id) DO UPDATE`（避免只传一个字段时 INSERT 侧 NOT NULL 约束失败）；
- 子任务 type 不可直接指定，从所属项目继承，保持「项目类型 = 子任务类型」的一致性；
- today 视图三段的归属：逾期/今日只看 tasks（子任务+idea），跟进只看 projects(type='follow') JOIN follow_ups；项目本身不再出现在逾期/今日段。

## 6. 遇到的报错及解决方案

| 报错/问题 | 原因 | 解决方案 |
|-----------|------|----------|
| PATCH 项目只传 nextFollowDate 时 500：`NOT NULL constraint failed: follow_ups.person` | upsert 的 INSERT 侧先校验 NOT NULL，person 传 NULL 直接失败，ON CONFLICT 来不及生效 | 先 SELECT 现有 follow_ups 行，与请求字段合并后再 INSERT ... ON CONFLICT DO UPDATE；合并后仍缺字段则 400 |
| 验证脚本中 `GET /api/projects` 计数为 1、分组名称为空 | PS 5.1 的 Invoke-RestMethod 把顶层 JSON 数组作为单个管道对象输出，`@()` 收到嵌套数组 | Api 函数内先 `$r = Invoke-RestMethod` 存变量再 `return $r`，利用函数返回的枚举特性摊平数组 |
| 首次 `pnpm --filter server build` 退出码 3221226505 | pnpm shim 偶发崩溃（npx tsc 直接跑正常） | 重跑即过，最终以 build exit=0 为准 |
