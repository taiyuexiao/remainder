# 多人协作 × 多 Agent：调研报告与方案

## 一、先确认我对你观点的理解

你说了三件事，我把它们提炼成三个判断和一个设想：

**判断 1：超级个体已成熟，超级团队未成熟。** 一个人 + 自己的 Agent 团队（coding/调研/写作 agent），内部指令是持续的、上下文是共享的，协作无门槛，全链路可跑通。但当任务大到需要多个人时，组织形式没有答案。

**判断 2：核心矛盾是「认知割裂」。** 这是你最锋利的洞察——在 vibe coding 模式下，操作和**思维**都外包给了 Agent。对一个任务"是如何被执行、将如何执行"，最清楚的是 Agent 而不是人。于是协作时出现了荒诞的降级：Agent 内部通信无门槛，人与人通信无门槛，**但各自的 Agent 团队之间是完全隔离的**，人被迫退化为"复制粘贴中继"——把 Agent 的总结、文档、问答搬运给另一个人和他的 Agent。

**判断 3：现有模式都不够。** DDD/SDD 文档驱动 + Git 分支合并的模式"能用但不灵活"；新人团队连 Gitee 规范都一头雾水，把仓库+文档+飞书微信指令全丢给 Agent 理解"显然不成熟"。

**你的设想：** 一个云端主 Agent，实时/低延迟扫描每个人电脑上的 Agent 在做什么，通过上下游依赖的接口对接、冲突解决、实时指导来协调。

**附加问题：** 团队知识沉淀（文档/经验/文章/讨论/情报）需要同时服务人和 Agent 两个消费者，且要解决信息分级问题（一个群太乱、多个群太多、工作入口只有一个）。形态上是不是还是 BBS/论坛？

我的结论先说：**你的问题诊断非常准确，但"云端主 Agent 实时扫描"的形态需要修正；知识平台不该是 BBS。** 下面用调研证据展开。

## 二、调研发现

### 2.1 学术界（arXiv）：agent 间协作靠"结构化工件"，不靠聊天

| 项目 | 核心机制 | 对你问题的启示 |
|---|---|---|
| **ChatDev**（清华/面壁，arXiv:2307.07924） | 虚拟软件公司，瀑布模型四阶段，每阶段 Instructor/Assistant 双角色"原子聊天" | 角色专业化 + 流程化交接 |
| **MetaGPT**（ICLR'24 Oral，arXiv:2308.00352） | 把人类 SOP 编码进 prompt 序列，**角色间用结构化文档（PRD/设计稿/接口规范）+ 发布-订阅机制通信，而非自由对话**，解决"级联幻觉" | 最重要的一条证据：多 agent 协作的教训是"聊天会失真，文档不失真" |
| **CTC 跨团队协作**（arXiv:2406.08979） | 多个 agent 团队并行提出不同决策方案再交叉沟通 | "多团队"开始被研究，但仍是单任务内 |
| **MultiAgentBench**（ACL 2025） | 首个系统评估多 agent 协作/沟通质量的基准 | "协作质量"本身成为研究对象，说明确实在早期 |

学术界的边界很清楚：**这些全是"一个任务内部"的角色扮演，没有一个人尝试过"跨人、跨设备、持久存在"的 agent 团队间协作。** 你踩的正是研究空白区。

### 2.2 协议层（Google/Anthropic/Linux 基金会）：你要的"agent 间直接交流"正在被标准化

- **MCP**（Anthropic，2024.11）：解决 Agent ↔ 工具/数据。到 2026.3 安装量超 9700 万次、1.2 万+ MCP server。
- **A2A（Agent2Agent）**（Google，2025.4 发布，同年 6 月捐给 Linux 基金会）：解决 **Agent ↔ Agent**。核心概念恰好对应你的需求：**Agent Card**（能力名片，互相发现）、**Task 生命周期**（submitted→working→input-required→completed，支持跨小时/天的异步任务）、**Message & Artifact**（交换的不只是对话，还有结构化产出物）。2026 年 v1.0 已稳定，150+ 组织在生产使用。
- MCP 与 A2A 已统一到 Linux 基金会 Agentic AI Foundation 治理，IETF 也开始起草 agent 网络基础设施草案。Gartner 称之为 Agent 的"TCP/IP 时刻"。

**但注意 A2A 的定位**：它是"任务委托"协议——你的 Agent 发现我的 Agent 的名片，把一个结构化任务委托给它，拿回 Artifact。**它不是"共享思维流"协议。** 这个区别对你第三节的方案设计至关重要。

### 2.3 商业产品：工业界收敛到了什么形态

**① 异步 Coding Agent 成为主流协作单元。** GitHub Copilot coding agent（把 issue 指派给 Copilot → 在 Actions 沙箱干活 → 自动开 PR 给人审）、Cognition Devin、Google Jules、OpenAI Codex 云端任务、Cursor background agents——所有头部产品收敛到同一形态：**Agent 在云端沙箱异步干活，产出物是 PR，协作媒介仍然是 Git，人在 PR 层对齐。** 也就是说，工业界目前给出的答案是：不解决"agent 间思维互通"，而是把**交接面压缩到 PR 这个已经被验证了 20 年的契约上**。

**② SDD（规格驱动开发）爆发。** GitHub Spec Kit、AWS Kiro（自动生成 product.md/structure.md/tech.md 三个 steering 文件约束 agent 行为）、Tessl、Fission OpenSpec、阿里 Qoder。共识是：**spec 取代代码成为人和 AI 共同的"单一真相源"**，分 spec-first → spec-anchored → spec-as-source 三层演进。你说的"每个子模块附文档写明任务/产出/接口"正是这条路线，它是对的，只是需要工具化。

**③ 团队级 agent 治理工具开始出现。** 腾讯开源 teamai-cli（统一管理 9 款 coding agent 的 Skill/Rules/MCP/Hooks，Git 原生分发，团队知识库召回）；GitHub 上的 AI-Coding-Collaboration-Paradigm 模板（让用不同 AI 工具的人共享同一套"工程口径"：架构推理、任务边界协议、验证命令、review 路径）；Anthropic 发布《AI-Native SDLC Playbook》（核心判断：代码不再是瓶颈，**瓶颈转移到规划、评审、测试**——治理必须跟上 agent 的速度）。

**④ 你设想的"agent 实时互通信"方向已有实验性开源项目**：agent-comm（agents 注册能力、互相发现、消息/广播、文件锁、共享 KV）；TeamMCP（去中心化，agents 像真实团队一样在 channel/DM 里自由协作）；codex-teams；Agent-MCP（共享知识图谱 + 任务管理）。**它们都还很早期、小众、评级不高**——这印证了你的判断"处于探索与讨论阶段"。

### 2.4 反方证据（做方案前必须知道）

- **Cognition《Don't Build Multi-Agents》（2025.6）**：在 coding 这种**高依赖、紧耦合**任务上，多 agent 系统极其脆弱。原则："Share context, not messages"——子 agent 只收到一条任务消息而看不到完整上下文，产出必然互相矛盾；"行动隐含决策"，分包即埋雷。
- **Anthropic 多智能体研究系统**：多 agent 在**低依赖、可并行**的研究类任务上效果显著，但 Anthropic 自己明确说："需要所有 agent 共享同一上下文、或 agent 间存在大量依赖的任务，目前不适合多智能体系统。"

**这两家顶级 agent 公司的共识是：思维层面的实时互通是坑，工件层面的结构化交接是路。**

### 2.5 记忆与知识基础设施

- 共享记忆：mem0（41k star，跨会话事实记忆）、Zep/Graphiti（双时态知识图谱，区分"事件发生时间"和"记录时间"）、Letta（共享 memory block 给多个 agent）；社区已有共识文章《Shared Memory: The Missing Brain of Multi-Agent AI》。
- 企业知识治理：腾讯云 Agent Memory 提出 L0 原始对话 → L1 事实原子 → L2 场景 → L3 画像的分层，以及 Memory Asset + ACL（**哪个 agent 能带走哪些知识，要有权限层**）；企业 AI 知识库 2.0 的教训是：60% 的 RAG 失败源于**时效性与一致性问题**而非检索质量，且 RAG/知识图谱之上还有"语义统一"（Ontology）问题——同一个词在不同人口中意思不同。

## 三、我的观点：修正你的"云端主 Agent"

你的方向是对的——**需要一个团队级的 agent 协调层**。但形态上有三个修正：

### 修正 1：不要"实时扫描每台电脑上的 agent 在想什么"，要"事件驱动 + 共享工件层"

实时扫描思维流有四个致命问题：隐私与权限（本地 agent 上下文里混着私人对话）、本地状态不可靠（电脑合盖就断）、思维流 90% 是噪音（试错过程不值得同步）、token 成本爆炸。**正确的抽象是：每个人的 agent 把"决策结果"以结构化工件的形式沉淀到共享层（git 仓、spec、任务板、知识库），云端协调者订阅这些工件仓库的事件（webhook），而不是窥探本地过程。** Git 本身就是人类发明过的最成功的"多人异步协作协议"，PR 就是 Artifact，CI 就是自动校验——vibe coding 时代不需要推翻它，需要把 agent 接进它。

### 修正 2：不要"agent 间自由对话"，要"结构化工件交换"

MetaGPT 的论文结论和 Cognition 的血的教训在这里汇合：人与人之间的语言是抗歧义的（可以追问、可以察言观色），**agent 之间的自然语言对话会级联失真**——第一轮只是含糊，第三轮已经变成另一个项目。所以 agent 间协作的媒介应该是：接口契约（OpenAPI/Proto）、spec 文档、测试用例、结构化任务卡——**有 schema、可校验、可 diff 的东西**。人与人之间的交流继续用语言；agent 与 agent 之间的交流用 schema。A2A 协议把交互建模为"Task + Artifact"而非"聊天"，正是这个逻辑。

### 修正 3：主 Agent 不是"监工"，是"平台工程师 + 契约守护者"

它不该实时指导每个人怎么写代码（那是微观管理，且会制造单点瓶颈和上下文瓶颈），它的职责应该是四件事：**维护模块依赖图与接口契约表；在 PR/CI 层面做冲突检测和契约测试（A 模块的产出是否还满足 B 模块的接口假设）；任务分发与认领；生成给 human 的分级 digest**。决策冲突升级给人，而不是自己拍板。

### 参考架构（四层）

```
L4 人机界面层：任务看板 + 分级信息流（必达/订阅/检索三级）
L3 编排层：云端 Coordinator——订阅 git webhook，维护依赖图，
            契约 CI，任务分发，digest 生成（可用 A2A 与各端 agent 委托任务）
L2 上下文层：AGENTS.md + steering rules + 团队知识库（MCP 化）+ 共享记忆
L1 工件层：monorepo（代码 + specs/ + docs/ + 接口契约）——唯一真相源
```

### 对你们新人 Java 团队的落地清单（按优先级）

1. **本周可做**：monorepo + 根目录 AGENTS.md（写明架构、目录职责、验证命令、"修改接口必须先改契约文档"）；每个模块一个 `SPEC.md`（任务/接口/产出/负责人）；PR 模板强制填写"影响哪些下游模块"。
2. **两周内**：CI 加契约测试（用 Spring Cloud Contract 或 Pact，接口变了下游立刻红）；用 Spec Kit 或 Kiro 的 steering 机制把 mentor 的口头规范沉淀成文件——**规范一旦进了仓库，agent 自动遵守，不再需要人转述**。
3. **一个月内**：团队知识库 MCP 化（见第四节）；git webhook 接一个简单的 digest bot，每天汇总"昨天谁动了哪些模块、哪些接口变了"。
4. **再往后**：等 A2A 生态成熟，各端 agent 以 Agent Card 注册能力，Coordinator 以任务委托方式协调——这是你原始设想的终态，但它应该建立在 L1/L2 稳固之后。

**演进原则：先把"工件"规范化（不依赖任何新工具），再知识化，再事件化，最后才是 agent-to-agent。跳过前三步直接上第四步，就是 Cognition 警告过的那种脆弱系统。**

## 四、知识沉淀与共享平台方案

### 为什么不是 BBS

BBS/论坛的三个结构性缺陷，恰好都踩在你的需求上：**它只为人类读者设计**（agent 检索帖子流的效果远差于结构化文档）；**它的组织单元是"帖子+时间线"**，而你需要的组织单元是"知识条目+频道+时效"；**它解决不了信息分级**——"zcode 注册送 3 亿 token"和"接口契约变更"在 BBS 里是同等重量的帖子，这正是你说的"放一个群太乱"的根源。

### 设计原则：一处沉淀，多处分发，分级消费

**① 内容模型：一切皆是"知识条目"，而非帖子。** 每条目带 frontmatter：`type`（文档 spec / 经验 note / 文章分享 share / 讨论 rfc / 情报 intel）、`tags`、`owner`、`created`、`ttl`（时效，比如"送 token"这种 7 天过期）、`acl`。类型决定分发策略，而不是"发在哪个版块"。

**② 消费分级，而不是分群。** 你的"群太多/群太乱"困境，本质是**用"群"这个维度同时承担了分类和通知两个职责**。拆开来：
- **必达**：@你、任务指派、接口契约变更影响到了你的模块 → 强通知；
- **订阅**：你订阅的频道（如"Java 后端""AI 情报"）→ 每日/每周 digest，不实时打扰；
- **检索**：不订阅也不通知，但 agent 在干活时能随时搜到。

**③ 讨论挂在知识条目旁，不进入聊天流。** 想发起探讨 → 对该条目开一个 RFC/issue 式讨论，结论回流更新条目本身。聊天是入口，仓库是归宿——群里/频道里的有价值内容，bot 自动（或打个标记）归档为条目，聊天流本身不需要被检索。

**④ 双消费者同一真相源。** 内容存为 markdown + git 托管：渲染成静态站给人看；通过 MCP server / RAG 给 agent 查。**不要建两个库**（一个 wiki 给人、一个向量库给 agent），那会立刻陷入"60% RAG 失败源于时效与一致性"的坑。

### 推荐形态：「团队知识仓库」

```
knowledge-repo/            ← git 仓，唯一真相源
├── specs/                 ← 模块文档与接口契约（与代码仓关联）
├── notes/                 ← 个人经验/踩坑（署名，可被引用）
├── shares/                ← 推荐文章 + 一句话点评（为什么值得看）
├── rfcs/                  ← 探讨帖（有结论后结论回填条目）
└── intel/                 ← 情报（AI 新闻/福利，短 TTL，只进 digest）
        ↓ 三个出口
① VitePress/Docusaurus 静态站      → 人看（搜索/订阅/评论）
② MCP server 或 RAG（Onyx/Dify/AnythingLLM/MaxKB 任一）→ agent 查
③ 频道 bot                          → 归档入口 + 每日 digest + 必达通知
```

### 现成选型

| 路线 | 工具 | 适合 |
|---|---|---|
| 全 SaaS（最省事） | 飞书知识库 + 话题群 + 多维表格做任务板；Notion AI；Glean 类企业搜索 | 不想维护任何东西，接受 agent 侧能力受平台限制 |
| 开源自建（agent 友好） | git + VitePress + **Onyx（原 Danswer）**/AnythingLLM 做检索层 + 自写归档 bot | 你们这种技术团队，agent 可读性最好 |
| 论坛补强（如果真要讨论区） | Discourse（开源、API 完整、可被 agent 读写） | 讨论量大且需要沉淀公开线程时，替代 rfcs/ 目录 |
| 记忆层（进阶） | mem0 / Zep(Graphiti) 存"谁擅长什么、哪个方案被否决过"这类动态事实 | 条目库解决"文档"，记忆层解决"状态与关系" |

我的具体建议：**走开源自建路线，但第一周只做最小闭环**——建仓、定 frontmatter 规范、挂一个静态站、接一个 RAG（AnythingLLM 十分钟能跑）、写一个"群里发 `#归档` 自动入库 + 每晚 digest"的 bot。这五件事任何一件都不需要新发明，组合起来就是你描述的平台的 80%。

## 五、总结

1. 你诊断的"认知割裂"是真实且被研究界/工业界共同确认的空白：学术界（ChatDev/MetaGPT 系）只解决了单任务内的多 agent 分工；工业界（Copilot/Devin/Jules）绕开了问题，把协作面压缩回 Git/PR。
2. 你设想的"agent 团队互通"正沿两条轨道被标准化：**A2A 协议（任务委托+Artifact 交换）和团队级 harness（teamai-cli、协作范式模板、AGENTS.md）**——但都明确避开了"思维流实时共享"，因为 Cognition/Anthropic 都已证明那是脆弱路径。
3. 修正后的路线：**工件（git+spec）为真相源 → 知识 MCP 化 → 事件驱动协调 → 最后才是 A2A 任务委托**。云端主 agent 的角色是契约守护者与分发者，不是监工。
4. 知识平台不是 BBS，而是"**git 托管的知识条目仓 + 三个消费出口（人看静态站 / agent 走 MCP / 通知走分级 digest）**"，讨论以 RFC 形式挂在条目旁，聊天只是入口不是载体。

# 团队知识沉淀与共享平台 · 完整方案

> 定位：一个**同时服务人和 Agent 两个消费者**的团队知识系统。解决四个问题：知识散落（微信群/飞书/个人笔记）、信息分级（一个群太乱、多个群太多）、Agent 不可读、知识过期失鲜。
> 形态：**不是 BBS/论坛，而是「Git 知识仓 + 三个消费出口 + 分级信息流」**。

---

## 1. 核心设计原则

| 原则 | 说明 | 反面教材 |
|---|---|---|
| **一处沉淀，多处分发** | 所有知识的唯一真相源是一个 Git 仓；网站、Agent 检索、群推送都只是"出口" | Wiki 一份、向量库一份、群文件一份，三周后互不一致 |
| **人写给人看，结构写给 Agent 看** | 正文是给人读的 markdown；frontmatter 元数据是给 Agent 读的 schema | 纯帖子里埋关键信息，Agent 检索全靠猜 |
| **消费分级，而非分群** | 用"必达 / 订阅 / 检索"三级消费替代"建多个群" | 开发群、推进群、学习群、消息群……群本身就是噪音源 |
| **聊天是入口，仓库是归宿** | 群里/频道里可以随便说，有价值的内容一键归档成条目，聊天流本身不承担沉淀职责 | 重要结论沉在群消息第 3000 条 |
| **写入零门槛，质量轻治理** | 发一条知识 ≤ 2 分钟；质量靠 TTL、owner、轻 review 保障，不靠前置审批 | 要填八张表才能发文档 → 没人写 |
| **知识有保质期** | 每类内容有默认 TTL，到期提醒 owner 确认/续期/归档 | 三年前的"环境搭建指南"还在误导新人 |

## 2. 总体架构

```
                        【写入入口】
  ┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────────┐
  │ 直接写 MD │  │ 群消息#归档│  │ 链接剪藏  │  │ Coding Agent  │
  │ 提 PR    │  │ bot 提炼  │  │ bot 抓取  │  │ 自动生成笔记  │
  └────┬─────┘  └────┬─────┘  └────┬─────┘  └──────┬───────┘
       └─────────────┴──────┬──────┴───────────────┘
                            ▼
              ┌──────────────────────────┐
              │   Git 知识仓（唯一真相源）  │
              │  markdown + frontmatter   │
              │  类型化 / 频道化 / 带 TTL  │
              └────────────┬─────────────┘
              ┌────────────┼─────────────┐
              ▼            ▼             ▼
        【出口1：人看】  【出口2：Agent查】 【出口3：推送】
        VitePress 静态站  MCP Server / RAG  飞书 bot
        搜索/浏览/订阅    kb_search 等工具   必达通知 + 分级 digest
```

## 3. 内容模型（这是整个方案的核心）

### 3.1 七种条目类型

| 类型 | 内容 | 例子 | 默认 TTL | 治理 |
|---|---|---|---|---|
| `spec` | 模块文档/接口契约 | 用户模块接口契约 v3 | 无 | 强：owner review + 变更必达通知下游 |
| `guide` | 工作文档/流程规范 | Gitee 分支规范、环境搭建、发布流程 | 90 天复核 | 强：频道 owner review |
| `note` | 个人经验/踩坑笔记 | "Spring 事务失效的三个坑" | 180 天复核 | 轻：任意 1 名同事 +1 即可 |
| `share` | 推荐文章/资源 | 链接 + 一句话点评（**为什么值得看**） | 无需复核 | 轻：免 review |
| `rfc` | 探讨/提案 | "要不要引入 MapStruct？" | 14 天无结论自动提醒 | 中：需有结论回填 |
| `intel` | 情报/快讯 | "zcode 注册送 3 亿 token" | **7~30 天** | 轻：免 review，只进 digest 不打扰 |
| `adr` | 架构决策记录 | "为什么选 MyBatis-Plus 而非 JPA" | 无 | 强：需相关方确认，**记录否决项** |

> `adr` 容易被忽略但对 Agent 极有价值：Agent 干活时最需要知道的不是"现状是什么"，而是"**当初为什么这么做、什么方案被否决过**"——避免它每次重新提议你们已经否决过的方案。

### 3.2 Frontmatter Schema（Agent 可读性的关键）

```yaml
---
type: note                      # spec|guide|note|share|rfc|intel|adr
title: Spring 事务自调用失效的三种场景
author: zhangsan
owners: [zhangsan]              # 责任人，过期提醒找 TA
channels: [backend]             # 决定进谁的 digest（订阅维度）
tags: [spring, transaction, java]  # 内容维度，供检索
created: 2026-09-05
ttl: 180d                       # 到期 bot 提醒 owner 续期/归档
status: active                  # rfc: open|concluded；其他: active|archived
acl: team                       # team(全团队)|project(项目组)|private(仅自己)
notify: digest                  # immediate(必达)|digest(进日报)|silent(只入库)
related: [spec-user-module]     # 关联条目，构建知识链接
---
正文给人看，自由 markdown。
```

`channels` 与 `tags` 分工：**tags 是"这是什么"（检索用），channels 是"谁该收到"（通知用）**。频道建议控制在 5~8 个：`backend` / `frontend` / `infra` / `product` / `ai-intel` / `learning` / `general`。

### 4.1 根目录 AGENTS.md（Agent 的第一入口）

```markdown
# 团队知识库 Agent 使用规范
- 开始任何开发任务前：先运行 kb_search 查相关 spec/adr/note
- 涉及接口变更：必须读取 specs/ 下对应契约，变更需同步修改契约文件
- 完成任务后：如遇到踩坑/方案否决/新约定，生成 note 或 adr 草稿（草稿目录 drafts/），等人确认合并
- adr/ 中的否决项是硬约束，不得重新提议
- intel/ 内容可能过期，引用前检查 TTL
- acl: private 的条目不可读取、不可引用
```

这一个文件，就把"知识库"变成了"团队所有 Agent 的共享记忆"——任何成员的 coding agent 启动时都会读到它。

## 5. 信息分级：三级消费模型（替代"分群"）

| 级别 | 触发条件 | 送达方式 | 例子 |
|---|---|---|---|
| **P0 必达** | @你；你是 owner 的 spec 发生变更；你负责的模块的下游接口变了；RFC 需要你做决策 | 飞书 bot 单聊即时推送 | "你负责的 user 模块上游契约 v3→v4，请确认兼容性" |
| **P1 订阅** | 你订阅的 channel 有新条目 | 每日 18:00 聚合 digest（一条消息，折叠式） | "今日 backend 频道：2 篇 note、1 个新 RFC；ai-intel：3 条情报" |
| **P2 检索** | 其余一切 | 不推送。人上静态站搜，Agent 走 kb_search | 三个月后有人踩到同样的坑，搜到了你的 note |

关键机制：**`notify` 字段由作者声明、owner 可改、bot 执行**。默认规则——`spec/adr` 变更对下游 owner 是 P0，其余全部默认 P1，`intel` 永远只进 digest。这样既不会漏掉接口变更，也不会被"送 token"这种事轰炸。

## 6. 四个写入工作流

### 6.1 直接写作（主路径）
clone 仓 → 从 `_templates/` 复制模板 → 写完提 PR → 按类型走对应轻 review → merge 后 CI 自动重建静态站 + 更新检索索引 + 触发分级通知。**全程 ≤ 2 分钟。**

### 6.2 群消息归档（消灭"沉在群里的知识"）
在飞书群里对某条消息回复 `#归档`（或转发给 bot）→ bot 用 LLM 提炼正文、自动生成 frontmatter 草稿（类型/标签/频道）→ 私聊发给原作者**一键确认/修改** → 入库。讨论串可整串归档成 `rfc`。

### 6.3 链接剪藏（share 类型）
把链接甩给 bot + 一句话点评 → bot 抓标题/摘要、生成 share 条目。**强制要求写点评**——"为什么值得看"才是给人和 Agent 的真正价值，裸链接没有沉淀价值。

### 6.4 Agent 自动沉淀（进阶，也是"Knowledge Suggestion"思路）
Coding agent 完成任务后，按根 AGENTS.md 的要求把"踩坑/新约定/被否决方案"写成 note/adr **草稿**放 `drafts/`，digest 里列出待确认草稿，人一键确认入库。**机器生产、人审入库**——这是把 vibe coding 过程中流失掉的隐性知识捞回来的关键一环。

## 7. Agent 消费层：MCP Server 设计

给团队所有 coding agent（Claude Code / Cursor / Codex 等）统一接一个知识库 MCP server，暴露 6 个工具：

| 工具 | 作用 |
|---|---|
| `kb_search(query, type?, channel?)` | 混合检索（关键词 BM25 + 向量），返回条目 + 出处 |
| `kb_get(id)` | 取全文（自动检查 acl 与 TTL） |
| `kb_list_recent(channel, days)` | "最近 backend 频道有什么新东西" |
| `kb_constraints(module)` | 聚合该模块的 spec + adr 否决项 → **Agent 干活前必查** |
| `kb_who_knows(topic)` | 按 owners/作者统计，回答"这事问谁" |
| `kb_submit_draft(...)` | Agent 提交 note/adr 草稿，等人确认 |

落地两个选择：
- **快**：先用现成 RAG（AnythingLLM / Onyx / Dify / MaxKB 任一）挂载知识仓目录，Agent 通过其 API 查询——当天能用，但没有 acl/TTL 语义；
- **正**：自研一个薄 MCP server（读 git 仓 + SQLite 索引 + 上述 6 个工具），约 300~500 行代码，把 acl、TTL、`kb_constraints` 做进去——建议第二周做掉。

进阶再加**动态记忆层**（mem0 / Zep）：存"谁擅长什么、哪个方案上周被否决、当前各模块进度状态"这类高频变化的事实，与静态条目库互补。

## 8. 与开发协作的衔接

- **接口契约放代码仓**：`spec` 类内容跟随代码 monorepo 的 `docs/contracts/`（离代码近，改代码必须改契约，CI 做契约测试）。知识仓通过 CI 定时同步副本并索引——**真相源只有一个，但检索入口统一**。
- **新人 onboarding 包**：`guides/` 下固定四篇——环境搭建、Gitee 分支规范、模块地图、术语表。新人+其 Agent 第一天只读这四篇。
- mentor 在飞书里的指令：**一律 #归档 进 guides 或转成 spec/adr**，从"口头规范"变"文件规范"——规范进仓之后，所有人的 Agent 自动遵守，不再依赖人转述。

## 9. 技术选型

| 组件 | 推荐 | 备选 | 理由 |
|---|---|---|---|
| 存储 | **Git 仓（Gitee 私仓）** | — | 版本、review、diff、权限全免费自带 |
| 静态站 | **VitePress** | Docusaurus / Outline / BookStack | 半小时搭好，搜索/侧边栏开箱即用 |
| 检索/Agent 层 | **自研薄 MCP server**（第二阶段） | AnythingLLM（第一阶段过渡）、Onyx、Dify、MaxKB | 现成 RAG 快但缺 acl/TTL；薄服务把这些语义补上 |
| Bot | **飞书开放平台自建 bot**（lark-oapi SDK） | 企业微信 bot | 你们已在飞书；微信个人号没有合规 bot 能力，只作只读转发 |
| 讨论 | **RFC 条目 + PR 评论** | giscus（静态站评论）、Discourse | 小团队阶段不需要论坛 |
| 定时任务 | bot 内置 scheduler / Git 仓 CI 定时 | — | digest、TTL 提醒、草稿待办汇总 |

如果未来完全不想自建，全 SaaS 退路是「飞书知识库 + 话题群 + 飞书智能伙伴」，但 **Agent 可读性会受平台 API 限制**，且无法承载 acl/TTL/schema——对你们这种 Agent 重度团队，建议自建。

## 10. 实施计划

**第一周（MVP，每天 1~2 小时）**

## 12. 三个最容易踩的坑

1. **一开始就建大而全的分类体系** → 先用 7 种类型 + 5~8 个频道跑起来，分类是长出来的，不是设计出来的。

# 知识平台作为「多人 × 多 Agent 协作」的子模块：能力实现机制

## 1. 先定位：它在协作架构里到底承担什么角色

回到你最初的核心矛盾——**对任务最清楚的是 Agent，而各自的 Agent 团队之间是割裂的**。拆开来，这个割裂其实是三种"不知道"：

| 割裂 | 具体表现 | 对应能力 |
|---|---|---|
| **事实割裂** | 别人的模块改了什么、接口变成什么样，我的 Agent 不知道 | 知识平台的**读能力**（spec/adr 检索） |
| **意图割裂** | 为什么这么设计、什么方案被否决过，我的 Agent 不知道，会重复犯错 | 知识平台的**约束能力**（adr 否决项、AGENTS.md） |
| **状态割裂** | 别人正在做什么、进度到哪、谁负责什么，人和 Agent 都不知道 | 知识平台的**同步能力**（分级 digest/必达） |

所以在四层架构里，知识平台不是独立产品，它是 **L2 上下文层**——团队所有 Agent 的"共享记忆体"，同时向 L4（人）提供信息流出口：

```
L4 人机界面层：任务看板 + 信息流 ──► 知识平台的 digest/必达通知出口
L3 编排层：Coordinator ──────────► 查 kb_who_knows 派活、查 spec 依赖图检测冲突
L2 上下文层：★ 知识平台 ★ ───────► 所有人的所有 Agent 的共享记忆（本模块）
L1 工件层：代码仓 + spec 契约 ────► spec/adr 类知识与此双向同步
```

一句话：**代码仓回答"系统现在是什么样"，知识平台回答"为什么是这样、谁在做什么、大家约定怎么做"——后者正是人和 Agent 对齐认知所需的全部非代码上下文。**

## 2. 能力实现的三个闭环

这套能力的本质是把"每个人的 Agent 各自脑内的上下文"外化成**一个共享、可检索、可约束的公共上下文**。通过三个闭环运转：

### 闭环 ① 读：Agent 干活之前，先"回到团队现场"

每个成员的 coding agent 启动时读到根 AGENTS.md，被强制要求：

```
开始任务 → kb_constraints(模块) → 拿到该模块的 spec + adr 否决项
        → kb_search(相关主题)   → 拿到别人沉淀的 note（踩坑记录）
        → kb_list_recent        → 拿到近期相关变更
```

**这解决"认知割裂"的关键不在检索技术，而在根 AGENTS.md 把查询变成了强制动作**——Agent 不是"可以查"，而是"必须先查再动手"。你的 Agent 不再是一个从零开始、只认识你一个人的孤儿，它每次干活前都自动回到了团队的最新认知现场。

### 闭环 ② 写：Agent 干活之后，把隐性知识捞回来

Vibe coding 最大的浪费是：Agent 排查两小时发现一个坑，这个认知只留在你电脑的会话记录里，下周另一个人的 Agent 重新踩一遍。闭环②堵这个口：

```
任务完成 → Agent 按 AGENTS.md 要求自检：
           "本次是否遇到踩坑？是否否决过某方案？是否形成新约定？"
        → 有则生成 note/adr 草稿（drafts/）
        → 进入当晚 digest 的"待确认"区
        → 人一键确认 → 入库 → 全员 Agent 下次可读
```

**机器生产、人审入库**。人不做知识的生产者（太累，坚持不下去），只做质检员（点一下确认）。这就是为什么这套系统能运转而传统 wiki 会死——写入成本从"写文档半小时"降到了"确认 5 秒钟"。

### 闭环 ③ 同步：人这一侧，用三级信息流保持对齐

Agent 之间靠工件对齐，人和人之间靠分级通知对齐：

- **P0 必达**：你是 owner 的 spec 变了、你的模块下游接口变了 → bot 单聊即时推给你。这类事少而重，必须到人；
- **P1 订阅**：你订阅频道的新条目（含待确认草稿）→ 每晚一条聚合 digest。扫一眼 30 秒，知道团队今天发生了什么；
- **P2 检索**：其余一切不打扰，人和 Agent 需要时自己查。

这就是你说的"一个群太乱、多个群太多"的解法——**不分群，分"送达级别"**。信息只有一份（在仓里），区别只在推多响。

## 3. 一个场景把三个闭环串起来

以你们新人 Java 团队为例，假设张三负责用户模块、李四负责订单模块：

1. **周一，mentor 在飞书群里说**"我们统一用 MyBatis-Plus，不用 JPA"。张三回复 `#归档` → bot 提炼成 adr 条目（含"JPA 被否决"及理由）→ 张三确认入库。**（闭环②）**
2. **当晚**，全员 digest 出现这条 adr。**（闭环③）** 没人需要翻群消息。
3. **周二，李四的 Agent 开发订单模块**，启动时按 AGENTS.md 执行 `kb_constraints("订单")` → 读到 adr → 直接用 MyBatis-Plus 写代码，**不会提议 JPA**。李四全程不知道有这个规范，但他的 Agent 知道。**（闭环①）**
4. **周三，张三改用户模块接口**，PR 里同步改了 spec 契约 → merge 触发 CI → 依赖图发现李四是下游 → **bot 给李四发 P0 必达**："上游契约 v3→v4，请确认兼容性"。**（闭环③）**
5. **周四，李四的 Agent 联调时踩了事务自调用的坑**，排查 40 分钟解决 → Agent 自动生成 note 草稿 → 李四确认入库。**（闭环②）**
6. **下下周，王五的 Agent 在另一个模块遇到类似代码**，`kb_search` 命中李四的 note → **40 分钟的坑，10 秒绕过**。**（闭环①）**

注意这个过程中发生了什么：**张三、李四、王五三个人几乎没有直接沟通过，但他们三人的 Agent 团队通过知识平台完成了认知对齐**——规范被遵守了、冲突被预警了、坑被共享了。这就是"每个人的 Agent 团队之间不再割裂"的实际运转方式。

## 4. 与其他模块的接口（它如何支撑更大的协作系统）

知识平台不试图解决全部协作问题，它对架构里其他三层暴露四个"接口"：

| 对接方 | 知识平台提供什么 |
|---|---|
| **→ 每个人的 Agent 团队** | MCP 工具集（kb_search / kb_constraints / kb_submit_draft…），统一接入口，与具体用哪款 coding agent 无关 |
| **→ 云端 Coordinator（L3）** | `kb_who_knows`（按 owner/作者分布回答"这事该派给谁"）；spec 依赖图（做冲突检测的输入）；digest 数据（Coordinator 生成团队日报的原料） |
| **→ 代码仓（L1）** | spec/adr 与代码仓 `docs/contracts/` 双向同步——契约跟着代码走，知识平台统一索引和检索 |
| **→ 人（L4）** | 三级信息流 + 静态站 + 待确认草稿队列 |

## 5. 为什么这个形态能实现能力，而替代方案不行

| 替代方案 | 断在哪 |
|---|---|
| 群聊 + 文件转发 | 无结构、无 TTL、Agent 不可检索——三个闭环全部断裂 |
| 传统 Wiki（飞书文档/Confluence） | 闭环①勉强可用（Agent 能读 API 的话），闭环②断裂（写入全靠人自觉→没人写），闭环③断裂（无分级推送） |
| 纯 RAG 知识库 | 有检索无治理——没有 owner/TTL/adr 否决语义，60% 的 RAG 失败正是死于时效与一致性，等于闭环①接了一根会腐烂的管子 |
| Agent 间直接聊天互通 | 自然语言级联失真（MetaGPT/Cognition 的教训），且无持久化——聊完就忘，形不成资产 |
| **本方案：Git 知识仓 + schema 元数据 + 三闭环** | 工件可校验、写入门近乎零、Agent 强制消费、信息分级送达——三个闭环全部接通 |

**总结**：知识平台实现"多人协作"能力的方式，不是给人和 Agent 又造了一个交流场所，而是把团队协作所需的共享认知（事实、意图、状态）从各自脑内和聊天记录里，外化成一份**版本化的、Agent 强制消费的、按级别送达的公共记忆**——读、写、同步三个闭环让这份记忆持续新鲜。它上接 Coordinator 的调度，下接代码仓的契约，两侧分别喂养 Agent 和人，是整个"超级团队"架构里最先该建、也最容易建成的那一块。
