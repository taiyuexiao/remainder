## 0. TL;DR

1. **不要做 BBS，也不要做 Wiki 二选一**——正确答案是**按"时效性 × 正式度"分层的单一平台** + **流→知识的一键沉淀机制**
2. "群太乱"的解药已被 Zulip 证明：**频道 × 强制话题（topic）**双层结构，一个入口、不轰炸、可异步
3. 给 agent 看的正确姿势不是"读页面"而是 **MCP 查询接口**（Glean/Unblocked 已验证：agent 要的是合成的、带权限的、新鲜的答案）
4. 平台的核心飞轮：**任何一层的内容都能向上沉淀一层**（快讯→探讨→知识），沉淀物自动进 agent 可查询的知识库

## 1. 需求拆解：你到底要共享什么

| 内容类型 | 例子 | 时效性 | 正式度 | 主要读者 |
|---|---|---|---|---|
| **即时情报** | "zcode 注册送 3 亿 token" | 小时~天 | 零 | 人（先到先得） |
| **探讨/求助** | "这个接口设计大家怎么看" | 天~周 | 低 | 人 → 结论要留下 |
| **经验/笔记/好文** | "我踩过的 rembg 模型下载坑" | 月~年 | 中 | 人 + agent |
| **工作文档/spec** | 你负责模块的 SPEC/STATUS/DECISIONS | 项目周期 | 高 | 人 + agent |

你的痛点不是"没地方发"，而是：**这四类东西共用同一个通道时必然互相淹没**（一群太乱 / 多群太多 / 单入口轰炸）。

## 2. 调研结论

### 2.1 群消息问题的标准答案：Zulip 模型

- Slack 的 thread 是可选的 → 没人用 → 消息大河。Zulip 的 **topic 是强制的** → 每条消息必须归属一个话题
- 效果：度假回来看到的不是 200 条未读，而是一列话题名——只点你关心的
- 关键机制：**新消息把话题顶到上面，而不是在时间流里淹没**；话题可移动/改名/拆分
- 对我们的意义：**一个频道（团队）× 话题（事情）**就够了，不需要开发群/推进群/学习群/消息群四个群

### 2.2 知识库/文档层的选型参照

| 产品 | 模型 | 启发 |
|---|---|---|
| **Outline**（开源 32k★） | 集合 + 文档 + 实时协作，Markdown | 工作文档/spec 层的形态参照 |
| **BookStack**（开源 MIT） | 书架>书>章节>页 强制层级 | "防信息沉没"的结构约束哲学 |
| **Notion** | 数据库多视图 | 内容一库多视图（列表/看板/时间线） |
| **Apache Answer / Scoold**（开源） | 问答式知识社区 | 探讨层的形态参照（问答可标"已解决"） |
| **Glean** | 企业知识图谱 + AI 助手 + **MCP server** | 给 agent 看的商业标杆 |
| **Unblocked** | agent-native：查询即得合成答案 | "agents query knowledge, they don't read it" |

### 2.3 给 agent 看：四个必备属性（Unblocked 总结的 agent-ready 标准）

1. **程序化访问**：API/MCP server，搜索框不是给软件的接口
2. **查询时权限**：按调用者权限过滤，每次调用都过权限
3. **新鲜度模型**：持续重建索引 / 过期检测 / 验证周期
4. **冲突消解**：wiki 和代码不一致时，产品合成一个可辩护的答案，而不是把两个都丢给 agent 猜

### 2.4 arXiv 侧的印证

- 我们之前的调研（`多智能体协作调研报告.md`）已确认：MCP 是 agent↔知识的事实标准；MetaGPT 证明了"结构化中间文档"对 agent 协作的关键性
- AI-KM 2025 趋势：**AI-KM 共生**（知识管理和 AI 能力一起设计）、MCP 化 agentic 集成、联邦多模搜索

## 3. 产品方案：「分层信息流 + 可沉淀」平台

### 3.1 一句话定位

> **一个入口，四层结构：快讯流 / 探讨区 / 知识库 / 文档库，层与层之间一键沉淀，全部内容对 agent 开放查询。**

### 3.2 架构图

```
┌────────────────────────────────────────────────────┐
│                    一个入口                          │
│  ┌─────────┬─────────┬─────────┬─────────┐          │
│  │ L1 快讯  │ L2 探讨  │ L3 经验库 │ L4 工作库 │          │
│  │ (topic  │ (问答式, │ (笔记/好文│ (spec/文档│          │
│  │  流, TTL)│ 可标记   │  /推荐)   │ /模块文档)│          │
│  │         │  已解决) │          │          │          │
│  └────┬────┴────┬────┴────┬────┴────┬────┘          │
│       └─────────┴─────────┴─────────┘                │
│            ↑ 一键沉淀（向上升级）                       │
├────────────────────────────────────────────────────┤
│         统一检索 + MCP server（agent 从这里读）         │
└────────────────────────────────────────────────────┘
```

### 3.3 四层分别长什么样

**L1 快讯流（对应"即时情报"）**
- 形态：Zulip 式——一个频道，每条快讯强制带话题标签（如 #羊毛 #AI新闻 #工具更新）
- TTL 机制：默认 7 天后自动沉底（不删，只是不再出现在主视图）；有人回复则复活
- 关键：**不推送通知**。看快讯是主动的"刷一眼"，不是被动的"被打扰"——这就是反轰炸设计

**L2 探讨区（对应"发起探讨"）**
- 形态：问答式卡片（Apache Answer 模型）——标题 + 正文 + 回复 + 可标记"有结论"
- 标记有结论时弹"沉淀为经验？"→ 一键进 L3

**L3 经验库（对应"经验/笔记/好文"）**
- 形态：卡片流 + 标签 + 全文搜索；每条带"有用"计数
- 来源：L2 沉淀 + 直接发布 + 浏览器剪藏转发
- 每条可关联到具体模块/项目（给 L4 和 agent 建立链接）

**L4 工作库（对应"模块文档/spec"）**
- 形态：Outline 式文档树，按模块/项目组织
- 与 SPEC/STATUS/DECISIONS 三件套打通（多智能体方案的 L0/L1 层）

### 3.4 核心飞轮：沉淀机制

```
快讯里有人说"这个坑我踩过" → 一键 → L2 探讨（求细节）
探讨得出结论           → 一键 → L3 经验（结构化改写，LLM 辅助整理）
经验被反复引用         → 一键 → L4 文档（进模块的 DECISIONS.md）
```

每一步都可以让 LLM 帮忙把口语化讨论改写成结构化文档（Remainder 已有 AI 排版能力可复用）。

### 3.5 给 agent 的接口（MCP）

按 2.3 的四属性实现：
- `search_knowledge(query, layer?, module?)` → 合成答案 + 引用来源（不是丢一堆页面）
- `read_doc(id)` / `list_recent(layer, since)` 
- 新鲜度：内容带 `updated_at` + 每次查询实时索引（Remainder 的 FTS5 已具备）
- 权限：v1 单团队全可见（个人工具场景），多团队时再上查询时权限

### 3.6 反模式清单（明确不做）

- ❌ 不做 BBS 板块（那是把"群太乱"换成"板块太冷"）
- ❌ 不做强制推送通知（快讯层零推送，通知只给 L2/L4 的 @我 和评审请求）
- ❌ 不做实时聊天（这个平台的定位是"沉淀"，实时讨论回 IM 去做，做完把结论沉淀回来）
- ❌ 不让 agent 读原始页面（MCP 合成答案）

## 4. Remainder 落地路径

现有资产：文档（Tiptap 编辑器+文件夹+FTS5 全文搜索）/ 剪藏箱（双通道入站）/ AI 助手 / LLM 排版 / 时间轴。

| 阶段 | 内容 | 复用 |
|---|---|---|
| **K1 个人双层** | 文档库加"经验"分区（标签体系），快讯用 Inbox+标签模拟 | 现有文档/Inbox/搜索 |
| **K2 沉淀机制** | 剪藏/Inbox/AI 对话 → 一键转经验文档（已有"剪藏转文档"管线可扩展） | M11 convert 管线 + M16 AI 排版 |
| **K3 agent 接口** | server 加 MCP server 端点（search/read/list） | FTS5 搜索已就绪 |
| **K4 联机共享** | 两台 Remainder 实例共享知识库（配多智能体方案 E3） | 待建的联机层 |

K1 几乎零成本，今天就能用；K3 是让"我的 agent 和队友的 agent 共享同一个知识底座"的关键。

## 5. 联机问题（后补讨论）

**要不要联机？** 要——知识共享的价值全在“别人能看见”。但不是把 Remainder 推翻成 C/S，而是**本地优先 + 可选联机模式**：

| 形态 | 结论 |
|---|---|
| **A. 团队节点（选定）** | 一台机器跑 Remainder server 当团队主机（现在就是 Fastify，改监听 0.0.0.0 + 共享 token 即可），其他人连它；零运维、数据不出内网 |
| B. P2P 同步（CRDT/git 式） | 工程量大、冲突复杂，小团队不值得 |
| C. 云中转 | 要部署要运维要账号体系，过重 |

**联机最小改动清单**：server 可配 host + token；desktop 的 `API_BASE` 从写死 127.0.0.1 改为可配团队节点地址；内容模型加 `author` 字段；MCP server 天然支持远程。

**顺序纪律**：先在单机把“四层 + 沉淀”跑顺（K1/K2），联机是“把验证好的平台开放出去”（K4，与多智能体方案 E3 汇合）。先联机会陷入权限/账号泥潭而内容形态未验证。

**诚实备选**：团队明天就要用的话，先自托管 Outline 当文档库 + 群发快讯顶着，Remainder 的分层模型验证好了再迁——不要为了团队化牺牲“个人主动提醒”的核心定位。

## 6. 风险与边界

1. **冷启动**：L3/L4 没人写就死了——K1 先用起来，把"快讯转发+一键沉淀"的摩擦压到最低
2. **沉淀疲劳**：如果每条都要手动整理，没人坚持——LLM 改写必须一键完成（已有能力）
3. **权限后补**：v1 默认同团队全可见；出现跨团队需求再上权限（Glean 式查询时权限是目标态）
4. **不替代 IM**：实时沟通还在微信/飞书，本平台只管"值得留下的东西"
5. **联机纪律**：联机模式是“把验证好的平台开放出去”，不是起点（见第 5 节）
