## 1. 定位与设计原则

> **一个同时服务人和 Agent 的团队知识系统。不是 BBS，不是第二个群，是"分层信息流 + 结构化知识条目 + 一切可沉淀"。**

| 原则 | 含义 | 来源 |
|---|---|---|
| 一处沉淀，多处分发 | 唯一真相源；人看的界面、agent 的 MCP、通知的 digest 都只是出口 | 0905 |
| 人写给人看，结构写给 agent | 正文自由 markdown；元数据（类型/频道/TTL/owner/acl）是给 agent 的 schema | 0905 |
| 消费分级，而非分群 | P0 必达 / P1 订阅 digest / P2 检索，替代"建多个群" | 0905 |
| 快讯零推送 | L1 快讯永不主动打扰，看是主动行为 | v1 |
| 聊天是入口，仓库是归宿 | 群消息/剪藏/对话里值得留的一键归档；聊天流不承担沉淀 | 0905+v1 |
| 写入零门槛，质量轻治理 | 发一条 ≤2 分钟；质量靠 TTL+owner+轻 review，不靠前置审批 | 0905 |
| 知识有保质期 | 每类内容默认 TTL，到期提醒 owner 续期/归档 | 0905 |
| agent 先查再动手 | 根规范强制：干活前必查 kb_constraints | 0905 |
| 冲突要消解，不甩锅 | wiki 与代码不一致时，系统合成一个可辩护答案并标注分歧，不丢两个让 agent 猜 | v1 |

## 2. 内容模型（v2 核心）

### 2.1 七种条目类型 × 四层呈现

| 类型 | 内容 | 落到哪层 | 默认 TTL | 治理 | 通知默认 |
|---|---|---|---|---|---|
| `intel` 快讯 | AI 新闻/福利/工具更新（"zcode 送 3 亿 token"） | **L1 快讯流** | 7~30 天 | 免 review | P1（只进 digest，永不实时推） |
| `share` 分享 | 推荐文章 + **一句话点评（为什么值得看，必填）** | L3 经验库 | 无复核 | 免 review | P1 |
| `note` 经验 | 踩坑/笔记（"Spring 事务失效的三个坑"） | L3 经验库 | 180 天复核 | 轻（任意同事 +1） | P1 |
| `rfc` 探讨 | "要不要引入 MapStruct？" | **L2 探讨区** | 14 天无结论提醒 | 结论必须回填 | 发起 P1，@到人 P0 |
| `guide` 规范 | 流程文档（分支规范/环境搭建/发布流程） | L4 工作库 | 90 天复核 | 频道 owner review | P1 |
| `spec` 契约 | 模块接口契约（SPEC.md 同源） | L4 工作库 | 无 | **强**：owner review + 变更必达下游 | **变更对下游 owner P0** |
| `adr` 决策记录 | "为什么选 MyBatis-Plus 而非 JPA"（**含被否决项**） | L4 工作库 | 无 | **强**：相关方确认 | **新增/变更对相关人员 P0** |

> adr 是 agent 最需要的类型：agent 干活时最怕不知道"什么方案被否决过"，adr 否决项是硬约束，agent 不得重新提议。

### 2.2 元数据 Schema（存 DB 字段，导出 git 时转 frontmatter）

```
type:        intel|share|note|rfc|guide|spec|adr
title:       标题
author:      作者
owners:      [责任人]          # 过期提醒/变更确认找谁
channels:    [backend]         # 订阅维度：决定进谁的 digest
tags:        [spring, java]    # 检索维度：这是什么
created:     2026-09-05
ttl:         180d              # 到期提醒 owner 续期/归档
status:      active|archived   # rfc 另有 open|concluded
acl:         team|project|private
notify:      immediate|digest|silent   # 作者声明，owner 可改，bot 执行
related:     [spec-user-module]        # 关联条目，构建知识链接
```

**channels 与 tags 的分工**：tags 回答"这是什么"（检索用），channels 回答"谁该收到"（通知用）。频道控制在 5~8 个：backend / frontend / infra / product / ai-intel / learning / general。

## 3. 产品形态（Remainder 内，四层 UI）

```
Remainder 导航新增「📚 知识库」（或并入文档页做层切换）
├─ L1 快讯流：话题流式列表（每条强制挂话题标签），7 天沉底、回复复活、零推送
├─ L2 探讨区：问答卡片（标题+正文+回复），可标「有结论」→ 触发沉淀
├─ L3 经验库：卡片流 + channels/tags 过滤 + 全文搜索 + 「有用」计数
└─ L4 工作库：文档树（复用现有文档模块），spec/adr/guide 按模块组织
```

**层间关系是升级而非隔离**：任何层内容一键向上沉淀（快讯里的好料 → 探讨/经验；探讨出结论 → 经验/adr；经验被反复引用 → guide/spec）。

## 4. 三级消费模型（替代分群）

| 级别 | 触发 | 送达 | 例子 |
|---|---|---|---|
| **P0 必达** | @你；你 own 的 spec/adr 变更；你模块的下游接口变了；RFC 需你决策 | 即时通知（Remainder 系统通知/桌宠气泡） | "user 模块上游契约 v3→v4，请确认兼容性" |
| **P1 订阅** | 你订阅的 channel 有新条目（含待确认草稿） | **每晚 21:00 聚合 digest**（复用现有邮件日报通道，加一节"今日知识库动态"） | "今日 backend：2 篇 note、1 个新 RFC；ai-intel：3 条" |
| **P2 检索** | 其余一切 | 不推送，人和 agent 需要时自查 | 三个月后有人踩同样的坑，搜到你的 note |

**默认纪律**：spec/adr 变更对下游 owner 是 P0；其余全部默认 P1；intel 永远只进 digest。推送越少，每条越有人看。

## 5. 沉淀飞轮（双入口）

```
入口 A（人发起）：快讯/探讨/剪藏/AI 对话 →「沉淀」按钮 → LLM 一键改写成结构化条目 → 进 L3/L4
入口 B（机器发起）：coding agent 干完活自检「踩坑/否决/新约定？」→ 生成 note/adr 草稿进 drafts/
                  → 当晚 digest「待确认草稿」区 → 人一键确认入库
```

**机器生产、人审入库**：人不做生产者（太累坚持不下去），只做质检员（确认 5 秒）。这是传统 wiki 会死而这套能活的根本原因。

## 6. Agent 消费层（MCP server）

Remainder server 加 MCP 端点，暴露 6 个工具：

| 工具 | 作用 |
|---|---|
| `kb_search(query, type?, channel?)` | 混合检索（FTS5 关键词 + 后续可扩展向量），返回**合成答案 + 出处**（不丢原始页面） |
| `kb_get(id)` | 取全文（过 acl + TTL 检查） |
| `kb_list_recent(channel, days)` | "最近 backend 有什么新东西" |
| `kb_constraints(module)` | 聚合该模块 spec + adr 否决项 → **干活前必查** |
| `kb_who_knows(topic)` | 按 owners/作者分布回答"这事问谁" |
| `kb_submit_draft(...)` | agent 提交 note/adr 草稿（进 drafts 待人审） |

四属性全部落实：程序化访问（MCP）/ 查询时权限（acl 每次过）/ 新鲜度（TTL + FTS 实时）/ 冲突消解（合成答案标注分歧）。

**根 AGENTS.md（团队规范文件）**——agent 的第一入口：

```
- 开始任何开发任务前：先 kb_constraints(模块) + kb_search(相关主题)
- 涉及接口变更：必须读 specs/ 契约，变更必须同步改契约
- 完成任务后：踩坑/否决/新约定 → kb_submit_draft 草稿
- adr 否决项是硬约束，不得重新提议
- intel 内容可能过期，引用前查 TTL
- acl: private 不可读不可引用
```

## 7. 联机（团队协作开放方式）

沿用 v1 结论：**本地优先 + 团队节点**——一台机器跑 Remainder server 当团队主机（监听局域网 + 共享 token），其他人客户端填节点地址即可。MCP server 天然支持远程，agent 无感。

顺序纪律不变：单机跑顺四层+沉淀 → 再开联机。先联机会陷入权限/账号泥潭而形态未验证。

## 8. 真相源决策（v2 对两版的最大调和）

| 方案 | 判断 |
|---|---|
| 纯 git 仓（0905） | 版本/review/diff 免费，但割裂 Remainder 现有资产（编辑器/搜索/剪藏） |
| 纯 Remainder DB（v1） | 体验好但缺版本历史，agent 扫描要走 API |
| **v2：Remainder DB 为操作真相源 + git 镜像导出** | 日常读写全走 Remainder；每晚 digest 时把条目增量导出为 git 仓 markdown（frontmatter 化）——版本历史/外部分享/agent 文件扫描全有了，且不回两份真相（**git 是只读镜像，谁被检索谁是真相源**） |

## 9. 实施计划（融合 0905 的 MVP 纪律与 Remainder 资产）

**K1（第一周，单机 MVP）**
- D1：DB 加条目表（七类型 + schema 字段）；文档模块加层视图入口
- D2：L3 经验库 UI（卡片流+过滤+搜索）——复用文档编辑器
- D3：L1 快讯流 UI（话题流+TTL 沉底）；剪藏/Inbox 加「沉淀为经验/快讯」按钮
- D4：MCP server v1（kb_search/kb_get/kb_list_recent 三个先跑通）
- D5：digest 加"今日知识库动态"节（复用邮件日报）

**K2（第二~三周）**
- L2 探讨区 + RFC 结论回填 + 沉淀飞轮（LLM 一键改写）
- P0 规则引擎（spec/adr 变更 → 下游必达）
- agent 草稿闭环（drafts + digest 待确认区）
- 根 AGENTS.md 规范文件

**K3（第四周起）**
- kb_constraints / kb_who_knows / kb_submit_draft
- git 镜像导出（每晚）
- TTL 到期提醒 + 第一次大清理

**K4（运营期）**
- 月度"最有价值条目" digest 署名表扬
- 联机模式（团队节点）
- 度量看板

## 10. 度量指标（每月看一次）

| 指标 | 健康信号 |
|---|---|
| 周活跃贡献者 | ≥60% 团队成员 |
| agent 侧 kb_search 调用量 / 命中案例 | 上升，且出现"agent 引用知识库解决问题"的 digest 案例 |
| 重复提问率 | 能被已有条目直接回答的问题占比上升 |
| 过期条目比例 | <15% |
| drafts/ 确认率 | >70%（太低说明 agent 草稿质量差，调 AGENTS.md） |
| P0 推送量 | 每周 <5 条（超了说明 P0 规则太松，推送开始贬值） |

## 11. 风险红线（合并两版）

1. **分类长出来，不是设计出来**：先 7 类型 + 5~8 频道跑起来，别一开始建大而全体系
2. **别做成第二个群**：严守默认 P1/digest；P0 只给 spec/adr 变更
3. **只有一份真相**：外部文档（飞书等）允许存在，但只能作为 share 条目的外链被索引，核心知识必须进库
4. **agent 只能写草稿**：人审入库是质量底线；adr 否决项是硬约束
5. **联机是开放不是起点**：见 §7
