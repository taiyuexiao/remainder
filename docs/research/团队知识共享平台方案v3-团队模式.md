# 团队知识共享平台方案 v3 · 团队模式与联机协作

> 状态：调研+方案，待评审 ｜ 2026-09
> 前身：`团队知识共享平台方案v2-融合版.md`（K1 已落地为 M23）
> 新增需求：工作库项目化 / @人 / 发布与同步 / 文档评论 / 群聊 / 团队模式（创建/空间/权限/隔离）

---

## 0. TL;DR

1. **团队模式不要造 SaaS 多租户**——Remainder 用「**一个团队节点 = 一个租户**」（天然 database-per-tenant，最强隔离，零多租户 bug）
2. **工作库项目化**：直接复用任务模块的项目模型（项目>子项目>文档），不另造轮子
3. **发布/同步 = 发布制（publish）+ 拉取订阅（pull-subscribe）**，不推全量——别人空间是别人的，发布只给"可见权"，要不要同步进自己库由对方选
4. **评论**：条目级评论流（thread per item），挂在知识条目/文档上
5. **群聊**：不自研 IM——快讯层就是轻讨论；真群聊等 K4 再接 Zulip/Mattermost 自托管（或先观察使用强度）

## 1. 调研：团队模式是怎么做的

### 1.1 自托管协作工具的权限/隔离模型（Mattermost / Zulip / Rocket.Chat）

| 产品 | 组织单元 | 权限粒度 | 隔离 |
|---|---|---|---|
| **Mattermost** | Server → **Team** → Channel | LDAP/AD 同步 + 企业版 RBAC | team 级成员制 |
| **Zulip** | **Realm（组织）** → Stream → Topic | realm 级策略（谁能邀请/建流），user/admin 足够小团队 | realm 完全隔离（一服务可多 realm） |
| **Rocket.Chat** | Server → Room | admin/leader/moderator per room + guest 临时用户 | room 级 |
| **Slack** | Workspace → Channel | owner/admin/channel admin | workspace 隔离 |

**小团队共识**：realm/team 级粗权限 + 频道级成员制就够了，细粒度 RBAC 是企业需求，不是 5 人团队需求。

### 1.2 多租户架构三种模式（SaaS 文献）

| 模式 | 隔离 | 成本 | 适用 |
|---|---|---|---|
| 共享库共享 schema（tenant_id 过滤） | 弱（一个 bug 就跨租户泄漏） | 低 | SaaS 起步 |
| 共享库分 schema | 中 | 中 | 中型 |
| **租户独立库** | **最强** | 高 | 强合规 |

**Remainder 的天然优势**：团队节点模式 = 每个团队自己的机器跑自己的 server 和自己的 SQLite——**天然"租户独立库"**，多租户最难的隔离问题不存在（不同团队根本不在一个进程里）。

### 1.3 RBAC 层级（Auth0/WorkOS/Calimatic 文献）

L1 简单角色（admin/user/viewer）→ L2 权限解耦 → L3 角色继承 → L4 **组织域角色**（同一人在 A 团队是 admin、B 团队是 viewer）→ L5 资源级 ACL。

**v3 选型：L1 + L4 的杂交**：角色只有 owner/admin/member/viewer 四种，但**角色绑定在 team 域**上（一个人在团队 A 是 member，团队 B 可以是 viewer）。WorkOS 的教训要听：**enforcement 是一千个小检查，一个错就泄漏**——所以我们的授权集中在一个 hook 里做（见 §3.4）。

### 1.4 发布/订阅同步的参照

| 参照 | 模式 | 启发 |
|---|---|---|
| Notion 公开页 | 发布=生成只读链接 | 发布 ≠ 复制，发布 = 可见权 |
| Google 共享盘 | 订阅共享盘 ≠ 文件进我的盘 | **"同步进自己库"是显式动作**（复制/创建快捷方式） |
| ActivityPub | 关注即订阅，投递进收件箱 | 发布物进"订阅者收件箱"，对方决定收不收 |
| Git fork | fork = 拿副本自己改，upstream 可拉回更新 | 同步副本要记 upstream 指针，可拉更新 |

## 2. v3 需求 → 设计

### 2.1 工作库项目化（对齐任务模块的项目模型）

工作库不再是平铺条目，而是 **项目 → 子项目 → 文档/条目** 三层：

```
工作库
├── 📁 项目：评测平台建设（可 @人）
│   ├── 📁 子项目：数据集模块（@张三）
│   │   ├── 📄 接口契约 v3（spec 条目）
│   │   └── 📄 踩坑笔记（note 条目）
│   ├── 📄 架构决策：为什么用 MyBatis-Plus（adr）
│   └── 💬 RFC：要不要统一异常处理
```

- 复用 M10 的 projects 模型 + M23 的 knowledge_items：knowledge_items 加 `project_id`（可挂在任务项目上）；项目树沿用 doc_folders 的嵌套结构
- 新建项目时可 @负责人（owners 数组）；标签体系保持不变（channels/tags 照旧）

### 2.2 @人

- 条目 owners 字段升级为可 @：详情页 @+名字 加入 owners → 触发对该人的 P0 必达
- 群聊/评论里 @名字 → 必达
- 实现：users 表（团队节点上有成员清单），客户端输入 @ 时弹出成员选择

### 2.3 发布与同步（核心新机制）

**发布 ≠ 复制。发布 = 给可见权 + 进对方收件箱。**

```
我（节点 A）                          队友（节点 B）
项目/条目点「发布」
   ↓ 推送到团队节点（或 P2P 直连）
节点收件箱出现「张三发布了 评测平台建设」
   ↓
队友在收件箱看到 → 三个选择：
  ① 仅查看（只读，不进自己库）
  ② 同步进我的库（拉副本，记 upstream 指针）
  ③ 忽略
同步副本后续：上游更新 → 我的副本标记「有新版本」→ 一键拉新（fork 式）
```

- 数据模型：`publications`（发布记录：item_id, from_node, from_author, published_at）+ 条目加 `upstream_id`/`upstream_node`/`upstream_version`
- 权限：发布时可选 acl（team/project/private）→ 决定节点上谁能看见

### 2.4 评论

- 所有条目/文档支持评论流：`comments`（item_id, author, content, created_at, parent_id 支持楼中楼）
- 详情页底部评论列表 + 输入框；评论 @人 → 必达
- agent 可读评论（MCP `kb_get` 带评论摘要）

### 2.5 群聊

- v3 明确**不自研完整 IM**：快讯层已覆盖"轻讨论"
- 真群聊需求（实时、多轮）→ K4 阶段评估接 **Zulip/Mattermost 自托管**（人家的强制话题流/权限都现成）或先做最简单的"条目下实时讨论串"（评论+轮询刷新，不叫 IM）
- 红线：别让 Remainder 变成聊天软件（智源观点：执行流≠消息流）

### 2.6 团队模式（创建/空间/权限/隔离）

```
团队节点（一台机器的 Remainder server）
└── team（团队）：name, invite_token
    ├── members：user + role（owner/admin/member/viewer，绑定 team 域）
    ├── spaces（空间）：默认一个"主空间"；可加项目空间做软隔离
    └── 内容全带 team_id（天然隔离：别的团队节点根本看不到）
```

- **创建团队**：`POST /api/teams {name}` → 生成 invite_token（分享链接）
- **加入**：队友客户端输节点地址 + invite_token → 成为 member
- **权限矩阵（粗粒度，小团队够用）**：

| 动作 | owner | admin | member | viewer |
|---|---|---|---|---|
| 建/删团队、管成员 | ✓ | | | |
| 建项目/发条目/发布 | ✓ | ✓ | ✓ | |
| 评论/有用+1 | ✓ | ✓ | ✓ | ✓ |
| 查看（acl=team） | ✓ | ✓ | ✓ | ✓ |
| 查看（acl=project） | ✓ | ✓ | 项目成员 | 项目成员 |

- **隔离**：团队节点之间零共享（天然 database-per-tenant）；节点内用 team_id + acl 过滤

## 3. 架构（四层，与多智能体方案对齐）

```
L4 人机界面：Remainder 客户端（工作库项目树 + 条目 + 评论 + 收件箱）
L3 编排：     团队节点 server（发布路由 + digest + 权限 hook）
L2 上下文：   知识库（MCP 化，含评论/owners）+ AGENTS.md 强约束
L1 工件：     团队节点 SQLite（=该团队唯一真相源；git 镜像导出可选）
```

| 阶段 | 内容 | 依赖 |

## 5. 风险红线

1. **权限 enforcement 集中**：所有授权走一个 server hook（team + role + acl 三层一次判完），禁止散落在路由里（WorkOS 的"一千个小检查一个错就泄漏"教训）
2. **发布不是复制**：副本记 upstream，但**上游删除不回删下游副本**（否则一次误删连锁丢数据）
3. **viewer 不能只看不想写**：viewer 角色是给"只读成员"的，别默认给
4. **群聊不做**：评论 + 快讯已够；K5 再评估
5. **联机 token 必须换**：默认 token 写死在包里 = 白搭；首次建团队强制生成随机 token

## 8. 后补：OKF 格式对齐（2026-09）

**结论：OKF 是 agent 可读的最佳"格式"，但只是格式不是服务——与 MCP 互补不替代。**

- **查询接口**：MCP（agent 要的是问的工具）→ 我们 M23 已实现
- **交换/存储格式**：OKF（任何 agent 不用接我们 MCP 也能读）→ 待做

**行动项**：v2 方案 §8 的"git 镜像导出"落地时，按 **OKF v0.2** 规范写 frontmatter（type 必填 + stale_after/sources/status 用 OKF 字段名），我们的知识库导出包即为标准 OKF bundle，跨团队/跨工具互认。

## 9. 架构决策修订：单节点多团队软隔离（2026-09-06，用户拍板）

**推翻 §0/§6 的「一个团队节点 = 一个租户（独立 server + 独立 SQLite）」硬隔离原案，改为：单节点内多团队软隔离。**

- **决策**：一个 server + 一个 SQLite，`knowledge_items.team_id` + `team_members` 成员校验做隔离；一个「👥 团队」入口内直接切换多团队（M24 已实现）
- **理由**：当前阶段没必要搞太复杂（用户原话）；一人多团队时独立节点意味着切团队=换节点地址，体验割裂
- **风险控制**（回应 WorkOS 血训）：权限校验集中在 `server/src/services/teams.ts` 的 `isMember/isAdmin/roleOf` 三函数，所有 knowledge/teams 路由统一走它，禁止散落各自判断
- **原案的适用时机**：未来若团队间有强合规隔离需求（如不同公司共用一个节点），再演进到多节点；届时客户端存多节点地址+各自 token 做聚合即可，数据模型无需变
