# 多智能体协作调研报告：从超级个体到 Agent 团队间通信

> 调研时间：2026-09 ｜ 范围：arXiv 论文 / GitHub 开源项目 / 商业产品 / 行业观点
> 任务来源：Remainder M20 调研任务（只调研不执行）
> 核心命题：SDD 开发模式下，"我的 agent 扫描队友模块的 md 文档 → 动态感知全局进度与状态 → 接口对接、bug 处理、冲突解决"，即**不同人的 agent 团队之间的通信问题如何解决**

---

## 0. TL;DR（结论先行）

1. 你设想的"agent 扫描队友 md 感知状态"在学术上叫 **共享黑板（Blackboard）架构 + 规范即契约（Spec-as-Contract）**，2025 年已有成熟原型（MetaGPT 的中间文档机制就是它的雏形）
2. Agent 间通信协议 2025 年爆发并在 Linux 基金会下收敛：**MCP（agent↔工具）+ A2A（agent↔agent）** 是事实标准组合
3. "超级个体单干比多个超级个体协作效率高"有实证支持（arXiv 2405.17924：个体-AI 配对完成速度显著快于团队），**但 AI 加持的团队性能上限更高**——瓶颈不在生成速度，在**评审容量（review capacity）**和**接口对齐成本**
4. 落地方案推荐：**「Spec 黑板 + A2A 消息 + 人类仲裁」三层架构**（详见第 5 节），Remainder 可以按四级演进路径切入

## 1. 背景与问题拆解

用户问题可拆为四层：

| 层 | 问题 | 对应概念 |
|---|---|---|
| 感知 | agent 怎么知道队友做到哪了 | 状态共享 / 黑板架构 |
| 理解 | 怎么知道队友的模块接口长什么样 | Spec-as-Contract / SDD |
| 通信 | 两个 agent 怎么对话、协商、请求 | 协议（A2A/MCP/ACP/ANP） |
| 治理 | 冲突谁说了算、质量谁把关 | 仲裁 / 评审容量 / 人在环路 |

## 2. 学术调研（arXiv）

### 2.1 通信协议：从战国到收敛

2024-2025 年涌现的协议簇（来源：arXiv 2505.02279 协议互操作性综述、2606.19135 技术分类）：

| 协议 | 发起方 | 定位 | 类比 | 现状 |
|---|---|---|---|---|
| **MCP** | Anthropic, 2024.11 | agent↔工具（垂直） | "AI 界的 USB-C" | 2025.12 捐给 Linux 基金会，已成事实标准 |
| **A2A** | Google, 2025.4 | agent↔agent（水平） | "agent 协作的 HTTP" | 捐给 Linux 基金会，150+ 组织支持（AWS/微软/Salesforce/SAP） |
| **ACP** | IBM/BeeAI, 2025.3 | REST-first 企业消息 | 企业消息总线 | 2025.8 并入 A2A（LF AI & Data） |
| **ANP** | 社区 | 去中心化 agent 市场（W3C DID） | 开放互联网 agent 黄页 | 小众 |
| **AGNTCY** | Cisco | 开放 schema + SLIM 消息层 | 基础设施 | Linux 基金会下互操作 |

**A2A 关键机制**（你的场景直接可用）：
- **AgentCard**：`/.well-known/agent-card.json` 声明技能/端点/安全方案 → 解决"互相发现"
- **Task 八态生命周期**：submitted → working → input_required → auth_required → completed/failed/canceled/rejected → 解决"请求-响应-追问"
- **SSE 流式 + webhook 推送**：长任务跨连接跟踪 → 解决"异步进度感知"

**MCP 与 A2A 的分工**（多个来源一致）：MCP 让 agent 接上自己的工具和数据；A2A 让 agent 把子任务委派给对等 agent。生产系统通常两者组合。

### 2.2 多智能体软件工程（接口对齐的直接先例）

| 框架 | 机制 | 对你的启发 | 数据 |
|---|---|---|---|
| **MetaGPT** (arXiv 2308.00352) | 角色 SOP + **中间文档**（需求文档/设计文档/接口规格作为交接物） | "接口规格文档是 agent 间的交接契约"——正是你说的 md 扫描的可行先例 | HumanEval 85.9% Pass@1；中间文档显著减少幻觉传播 |
| **ChatDev** (Qian et al. 2024) | chat chain + **communicative dehallucination**（agent 被鼓励多轮追问细节而不是立刻回答） | 冲突解决靠"追问澄清"而非"立刻输出" | 质量分 0.395 vs MetaGPT 0.152 vs 单 agent 0.142 |
| **HyperAgent** (Phan et al. 2024) | Planner 发标准化消息（Context+Request 两字段）到**任务队列**，子 agent 异步消费 | 消息格式标准化 + 队列 = 可并行扩展 | 多 Navigator 并行探索代码库 |
| **AutoGen** (Microsoft, COLM 2024) | 自由多 agent 对话编排（两两/群组/层级委派） | 最灵活的通信底座，但无结构约束 | — |

### 2.3 失败模式（必须知道的坑）

**"Why Do Multi-Agent LLM Systems Fail?"（arXiv 2503.13657）** 归纳的失败模式：
- 规格遵循差、agent 间不对齐（忽略输入/隐瞒信息）
- 任务验证与终止判断失效
- **协调错误会级联**（coordination errors cascade）

**MultiAgentBench（arXiv 2503.01935）**：多 agent 协作/竞争的评测基准——说明"协作质量"本身已是可测量指标。

### 2.4 超级个体 vs 团队的实证

**arXiv 2405.17924（生成式 AI 与团队绩效实验）**：
- 个体-AI 配对完成任务**显著快于**人类团队（β=-0.659, p<.01）
- 多 AI 团队反而比单 AI 慢（β=0.128, p<.10）——**协作有协调税**
- 但 AI 加持的团队在总体性能上仍显著优于个体-AI 配对（β=0.422, p<.01）
- **结论：单任务速度 = 超级个体赢；性能上限 = AI 团队赢。协作的价值不在快，在正确性、覆盖面和责任分散**

行业观点佐证：
- 智源社区《Agent 范式转移》（2026.3）："一个懂业务取舍的骨干指挥一群 Agent，单点产出可超越过去十人团队"；但**把 agent 拉进人类聊天群是错的**——消息流为人类模糊性设计，agent 需要**执行流**（明确输入、依赖关系、步骤确认、证据交付）
- 腾讯云刘毅（2026.6）：个人侧效率提升 10 倍成超级个体，但"难以把超级个体连接起来"是组织侧卡点 → WorkBuddy 的方向就是"连接超级个体、形成上下文飞轮"

## 3. SDD（规范驱动开发）生态——你的"md 扫描"设想的现成轮子

| 工具 | 机制 | 与"agent 读 md 感知状态"的关系 |
|---|---|---|
| **GitHub Spec Kit**（MIT，开源） | constitution（宪法）→ specify → plan → tasks；spec 是 agent 的共享真相源 | spec 文件就是给 agent 读的 md；可直接被队友 agent 扫描 |
| **Amazon Kiro** | requirements.md/design.md/tasks.md 三文档 + EARS 语法 + Agent Hooks（文件保存触发自动动作） | **Hooks 就是"文件变更 → 触发 agent"的事件机制** |
| **OpenSpec** | specs/（当前真相）+ changes/（提案+delta）；严格状态机 | 最接近"接口变更提案 → 队友确认 → 合并"的协作流 |
| **Tessl** | spec-as-source：人只维护 spec，代码全由 agent 生成（文件头标 `GENERATED FROM SPEC - DO NOT EDIT`） | 最激进：spec 即代码，agent 间只需同步 spec |
| **BMAD-METHOD** | 21+ 角色 agent（分析/PM/架构/开发/QA）+ JSON 工件 + 跨 agent 一致性检查 | 宣称比 ad-hoc AI 编码快 55% |

Martin Fowler 站的 SDD 分层（fowler.com, 2025.10）：
1. **Spec-first**：先写 spec 再写码（最低级）
2. **Spec-anchored**：spec 活到功能生命周期结束（中级）
3. **Spec-as-source**：spec 是主工件，人不碰代码（终级）

## 4. 商业产品格局（agent 团队怎么卖）

| 产品 | 模式 | 协作机制 |
|---|---|---|
| **Devin**（Cognition） | 云端自治工程师，领任务→写码→跑测试→开 PR | Slack 频道汇报进度、追问澄清；长期项目记忆 |
| **Jules**（Google） | 异步任务代理（每天 20 免费任务） | GitHub 原生 PR 流 |
| **Copilot coding agent**（GitHub） | issue→PR | 嵌入 GitHub 既有评审流 |
| **Codex**（OpenAI） | 并行云端沙箱批量任务 | Terminal-Bench 88.8%；会话间无记忆是短板 |
| **Claude Code** | 终端深度工作 | **Agent Teams**：主 agent 派生子 agent 并行 + Routines 定时触发 |
| **腾讯 WorkBuddy/CodeBuddy** | 企业版办公智能体套件 | 明确主打"连接超级个体→超级团队" |

**多个来源共同强调的瓶颈**：不是模型能力，是**评审容量（review capacity）**——"选 agent 要看团队能多快验证产出；高自治只有团队验证够快时才划算"（daily.dev 2026 对比评测）。

## 5. 方案设计：Remainder/团队的 Agent 协作架构

### 5.1 核心理念

把你说的"agent 扫描队友 md"升级为三层：

```
┌─────────────────────────────────────────────────────┐
│ L3 治理层：人类仲裁 + 评审门禁（review capacity 决定上限）│
├─────────────────────────────────────────────────────┤
│ L2 通信层：A2A 消息（请求/追问/委派/回报）              │
├─────────────────────────────────────────────────────┤
│ L1 感知层：Spec 黑板（md = 状态 + 接口契约，全员可读）    │
├─────────────────────────────────────────────────────┤
│ L0 工件层：spec/进度/接口文档（git 版本化，唯一真相源）    │
└─────────────────────────────────────────────────────┘
```

### 5.2 各层设计

**L0/L1 —— Spec 黑板（对应你的"扫描 md"）**
- 每个模块目录维护三个 md：`SPEC.md`（接口契约：导出什么 API/事件/数据结构）、`STATUS.md`（进度：done/doing/blocked + 最后更新）、`DECISIONS.md`（关键取舍）
- 每个开发者的 agent 启动时 + 定时（如 10 分钟）扫描队友目录 → 构建"全局状态摘要"
- 扫描器实现极简：git pull + glob + LLM 摘要；Kiro 式 Hooks（文件变更即触发）
- 关键纪律（MetaGPT 经验）：**中间文档必须结构化**——agent 写 spec 用固定模板，机器可解析（frontmatter YAML + 正文）

**L2 —— 通信层（A2A 协议落地）**
- 每个开发者的 agent 暴露 A2A server（AgentCard 声明技能：`review_interface` / `answer_spec_question` / `propose_change`）
- 典型消息流：
  - 我的 agent 发现队友 SPEC.md 的接口和我预期不符 → 发 A2A task `input_required`："字段 X 的类型是 string 还是 number？"
  - 队友 agent 自动应答（读自己的 spec）或升级给人类（auth_required）
- 冲突处理（ChatDev 经验）：**先追问澄清，再动手改**；禁止 agent 直接改队友文件，只能提 PR/提案

**L3 —— 治理层**
- 接口变更走 OpenSpec 式提案流：`changes/` 目录提提案 → 相关方 agent 自动评审 → 人类点确认 → 归档进 specs/
- 仲裁规则：spec 冲突时以"最新人类确认版本"为准；agent 间的分歧超过 2 轮自动升级人类
- 度量（MultiAgentBench 思路）：跟踪"接口对齐耗时""冲突数/周""agent 自主解决率"

### 5.3 Remainder 的四级演进路径

| 级 | 内容 | 依赖 |
|---|---|---|
| **E1 个人增强**（现状+） | AI 助手/文档/排版已就绪；加"任务 spec 模板"（每个项目挂 SPEC.md 文档） | 现有 M19 |
| **E2 感知** | agent 定时扫描本地项目目录的 md → 全景页加"agent 动态摘要"（各模块状态一句话） | 现有 TimelinePage + LLM |
| **E3 联机** | server 加 A2A 端点（AgentCard + task 生命周期）；两人 Remainder 实例互连；任务排期对齐（共享只读 timeline）+ 文档共享（知识库联邦查询） | 网络部署 |
| **E4 协作闭环** | 接口提案流（changes/specs 目录）+ agent 间追问 + 人类仲裁台 | E3 稳定后 |

### 5.4 风险与红线

1. **评审容量是硬上限**——agent 产出的 PR/提案必须小于人类的评审带宽，否则协作净亏（daily.dev 结论）
2. **协议安全**：agent 间 prompt injection（arXiv 2410.07283：LLM-to-llm 注入）、agent 仿冒；A2A 的 auth_required 态要用起来
3. **别把 agent 塞进聊天群**（智源观点）：agent 间走结构化消息（执行流），人人才走消息流
4. **协调税真实存在**：2-3 个 agent 分工明确的任务才拆开做；能一个人（+agent）闭环的就别协作
